## 漏斗分析

### 页面介绍

漏斗分析页面用于分析用户在业务流程中的转化情况，通过可视化漏斗图展示用户在各个环节的流失和转化数据。

### 核心功能

1. **漏斗类型选择**
   - 支持用户级漏斗分析：以用户为单位，分析用户在整个转化流程中的行为
   - 支持会话级漏斗分析：以会话为单位，分析单次会话内的转化情况

2. **窗口期设置**
   - 可配置转化窗口期（如7天、14天、30天等）
   - 用于定义用户完成整个漏斗转化的时间范围

3. **漏斗配置**
   - 支持多步骤漏斗配置
   - 每个步骤可配置具体的事件和筛选条件
   - 支持自定义漏斗步骤顺序

4. **数据维度分析**
   - 支持按不同维度（如渠道、设备、地区等）进行分组分析
   - 可对比不同维度下的转化率差异

5. **全局筛选**
   - 支持对用户属性、事件属性等进行筛选
   - 可精确分析特定用户群体的转化情况

6. **时间范围选择**
   - 支持自定义时间范围查询
   - 默认显示最近7天的数据

7. **数据导出**
   - 支持将分析结果导出为文件
   - 支持异步导出任务，可下载导出文件

### 使用场景

- **电商转化分析**：分析从浏览商品 → 加入购物车 → 下单 → 支付的转化率
- **注册流程优化**：分析注册流程各步骤的流失情况，找出优化点
- **营销活动效果评估**：分析营销活动带来的用户转化效果
- **产品功能使用分析**：分析用户使用产品功能的完整流程转化情况
- **渠道效果对比**：对比不同渠道（如App、Web、小程序）的转化率差异

### 典型应用示例

- 分析"首页访问 → 商品详情页 → 加入购物车 → 结算 → 支付成功"的完整转化漏斗
- 对比不同设备类型（iOS、Android）的注册转化率
- 分析新用户与老用户在购买流程中的转化差异

## 事件分析

### 页面介绍

事件分析页面用于深入分析特定事件的触发情况，包括事件触发次数、触发用户数、事件属性分布等。

### 核心功能

1. **事件选择**
   - 支持选择单个或多个事件进行分析
   - 可查看事件的详细定义和属性

2. **全局筛选**
   - 支持对用户属性、事件属性进行筛选
   - 可精确分析特定条件下的事件触发情况

3. **数据维度分析**
   - 支持按不同维度（如时间、用户属性、事件属性等）进行分组
   - 可查看不同维度下的事件分布情况

4. **时间范围选择**
   - 支持自定义时间范围查询
   - 默认显示最近7天的数据

5. **数据表格展示**
   - 以表格形式展示详细的事件数据
   - 支持排序、筛选等操作

6. **数据导出**
   - 支持将分析结果导出为文件
   - 支持异步导出任务

### 使用场景

- **核心事件监控**：监控关键业务事件（如购买、注册、分享等）的触发情况
- **用户行为分析**：分析用户对特定功能的操作频率和习惯
- **异常事件排查**：当某个事件触发异常时，通过事件分析定位问题
- **A/B测试效果评估**：对比不同版本下事件触发率的差异
- **功能使用情况统计**：统计新功能上线后的使用情况

### 典型应用示例

- 分析"购买"事件在最近一周的触发趋势
- 对比不同地区用户对"分享"事件的使用情况
- 分析"搜索"事件中不同关键词的分布情况
- 监控"错误"事件的触发频率，及时发现系统问题

## 用户路径分析

### 页面介绍

用户路径分析页面用于分析用户在应用中的行为路径，了解用户从进入应用到完成目标行为的完整路径。

### 核心功能

1. **路径可视化**
   - 以图表形式展示用户的典型行为路径
   - 支持查看路径的转化率和流失点

2. **路径筛选**
   - 支持设置起始事件和结束事件
   - 可筛选特定用户群体的路径

3. **路径深度设置**
   - 可配置分析的路径深度（如3步、5步、10步等）
   - 支持查看不同深度的路径分析

4. **全局筛选**
   - 支持对用户属性、事件属性进行筛选
   - 可分析特定用户群体的行为路径

5. **时间范围选择**
   - 支持自定义时间范围查询
   - 默认显示最近7天的数据

6. **数据导出**
   - 支持将路径分析结果导出为文件

### 使用场景

- **用户行为洞察**：了解用户在使用产品时的典型行为路径
- **产品优化**：发现用户路径中的异常跳转或流失点，优化产品流程
- **新用户引导**：分析新用户的典型路径，优化新用户引导流程
- **功能关联分析**：发现功能之间的关联关系，优化功能布局
- **异常路径识别**：识别异常的用户行为路径，发现潜在问题

### 典型应用示例

- 分析用户从"首页"到"完成购买"的典型路径
- 对比新用户和老用户的行为路径差异
- 发现用户在注册流程中的异常跳转行为
- 分析用户在使用搜索功能后的后续行为路径

## 归因分析

### 页面介绍

归因分析页面用于分析转化事件的归因情况，帮助理解哪些营销渠道或用户行为对转化产生了贡献。

### 核心功能

1. **归因模型选择**
   - 支持多种归因模型：
     - 首次触达归因（First Touch）：将转化归因于用户首次接触的渠道
     - 末次触达归因（Last Touch）：将转化归因于用户最后接触的渠道
     - 线性归因（Linear）：将转化平均分配给所有接触点
     - 时间衰减归因（Time Decay）：根据时间距离分配权重
     - 位置归因（Position Based）：给首次和末次接触点更高权重

2. **转化指标配置**
   - 支持选择转化目标事件（如购买、注册等）
   - 可配置转化指标的维度分析

3. **归因事件配置**
   - 支持选择归因事件（如广告点击、页面浏览等）
   - 可配置归因事件的维度分析

4. **全局筛选**
   - 支持对用户属性、事件属性进行筛选
   - 可精确分析特定条件下的归因情况

5. **时间范围选择**
   - 支持自定义时间范围查询
   - 默认显示最近7天的数据

6. **数据表格展示**
   - 以表格形式展示归因分析结果
   - 支持按不同维度查看归因数据

7. **数据导出**
   - 支持将归因分析结果导出为文件

### 使用场景

- **营销渠道效果评估**：评估不同营销渠道对转化的贡献度
- **广告投放优化**：了解哪些广告渠道带来了实际转化，优化广告投放策略
- **用户获取分析**：分析新用户的来源渠道，优化用户获取策略
- **ROI计算**：结合成本数据，计算不同渠道的ROI
- **多触点归因**：理解用户转化过程中的多触点贡献

### 典型应用示例

- 分析"购买"转化在不同营销渠道（如搜索引擎、社交媒体、直接访问）的归因情况
- 使用首次触达归因，了解哪些渠道带来了新用户
- 使用末次触达归因，了解哪些渠道促成了最终转化
- 对比不同归因模型下的渠道贡献差异，制定更全面的营销策略

## UTM 分析

### 页面介绍

UTM 分析页面（`/data-analysis/utm`）用于分析各投放链接带来的流量效果。埋点上报里带的 UTM 参数（来源、媒介、活动、关键词、内容）在这里按维度组合交叉分析，输出各组合的事件数、用户数、会话数，回答「这次投放带来了多少人、哪个渠道最有效」。

### 核心功能

1. **UTM 分组维度**
   - 从来源（`utm_source`）、媒介（`utm_medium`）、活动（`utm_campaign`）、关键词（`utm_term`）、内容（`utm_content`）里任选 1~5 个维度，按组合交叉分析
   - 只选「来源」是看各来源的量；「来源 + 媒介」一起选则是看具体投放位的效果
   - 每个选中的分组维度都会排除空取值，即按「来源 + 媒介」分组时只统计两个维度都有值的流量

2. **数据指标**
   - 事件数、用户数、会话数，可多选
   - 第一个选中的指标决定汇总表的排序与趋势图的纵轴

3. **UTM 取值筛选**
   - 可只看某几个具体取值
   - 取值来自「埋点管理 > UTM 管理」里维护的条目，下拉中带别名展示（`别名（原始取值）`）

4. **全局筛选**
   - 支持对用户属性、事件属性等进行筛选，可精确分析特定人群的投放效果

5. **时间范围选择**
   - 支持自定义时间范围查询，默认显示最近 7 天的数据
   - 跨度上限 366 天

6. **趋势图**
   - 按天的指标趋势，展示「合计」与取值量最大的前 10 个分组

7. **汇总表**
   - 每个 UTM 取值组合一行，给出各指标在所选时间区间内的合计
   - 表格顶部的「合计」行是整个区间、不分组的去重汇总
   - 维度列展示原始取值，别名在 hover 中显示

8. **数据导出**
   - 支持将分析结果导出为 Excel，走异步导出任务

9. **保存为看板**
   - 可把当前分析配置存成看板卡片，放到首页统一查看

### 口径说明

- **合计不是分组行相加**：用户数、会话数是去重口径，同一个用户出现在多个分组里会被重复计数。所以合计行与趋势图的「合计」线都单独查询、按区间/按天去重，不从分组行汇总
- **与 UTM 管理的「累计事件数」口径不同**：UTM 管理页的累计统计来自清洗前的事件表，本页查询的是清洗后的事件表，两者数值不必相等

### 与 UTM 管理的关系

- **别名**：在「埋点管理 > UTM 管理」里给取值填了别名后，本页表格维度列 hover 可见别名，取值筛选器下拉显示「别名（原始取值）」
- **软删除**：在 UTM 管理里删掉某个取值后，它在本页**任何维度上都不再计入** —— 不只不作为分组行出现，它贡献的事件也不会算进其它维度的组合里。误删可在「已删除」页签里恢复

### 使用场景

- **投放效果评估**：对比不同来源、不同活动带来的用户数与会话数
- **渠道预算分配**：找出性价比最高的来源/媒介组合，指导下一轮预算分配
- **活动复盘**：按活动维度看某次营销活动整个周期的流量走势
- **关键词优化**：按关键词维度看搜索投放里哪些词真正带来了量
- **素材对比**：按内容维度对比同一批投放里不同素材的引流效果

### 典型应用示例

- 只按「来源」分组，看最近 30 天各来源的用户数排名
- 按「来源 + 媒介」交叉，找出 `google / cpc` 这类具体投放位的效果差异
- 用 UTM 取值筛选锁定某个活动，再按「内容」分组，对比该活动下不同素材的引流
- 删掉内部测试用的 UTM 取值，让报表不再被测试流量污染

## SQL 查询

### 页面介绍

SQL 查询页面（`/data-analysis/sql`）允许用户手写 SQL 直接查询 ClickHouse 中的数据，查询结果以表格形式展示，适用于灵活的自定义数据分析场景。

### 核心功能

1. **SQL 编辑器**
   - 内置 SQL 语法高亮编辑器，支持手写查询语句
   - 支持 `Cmd/Ctrl + Enter` 快捷键执行查询

2. **安全限制**
   - 仅支持单条 `SELECT`（含 `WITH`）查询，禁止 `INSERT`、`ALTER`、`DROP` 等写操作与 `EXPLAIN` 等元操作。关键字按位置判定：表达式后面的 `delete` / `set` / `update` 是别名（`SELECT (1) delete FROM (SELECT 1)` 是合法查询），`WITH x AS (SELECT 1) INSERT INTO …` 这种 CTE 之后的写语句才会被当成语句动词拦下
   - 服务端同时以 ClickHouse 的 `readonly = 2` 兜底：非查询语句与 DDL 由 ClickHouse 本身拒绝，`readonly` 自己也改不掉。但 `readonly = 2` 允许查询改**其它**设置，而且实测 `readonly` **兜不住会改写查询本身的那一类**（见下），所以真正的设置管控是下面几条
   - 不允许通过 `SETTINGS` 修改设置，几类都拦：
     - 会改写查询本身的：`select` / `order` / `sort` / `filter` / `format` / `limit` / `offset` / `page` 这 8 个的值会被 ClickHouse 当成 SQL 再解析一遍——实测 `SELECT 2 SETTINGS select = '1, version()'` 返回 `1	26.10.1.1`，把 `select=1, version()` 放进查询串里也一样生效，而它们在 `readonly = 1` 下全都返回 200。同一个类别还有 `database`（等于 `USE 别的库`）与 `implicit_table_at_top_level`（把没有 FROM 的查询指向别的表），这两个实测都能绕开下面的 `system` 库规则
     - 解除只读与约束（`readonly` / `constraints` / `changeable_in_readonly`）、出网与凭据（`use_environment_credentials` / `s3_allow_server_credentials_in_user_queries` / `ai_function_*`）、服务器文件路径与响应头（`user_files_path` / `user_scripts_path` / `http_response_headers`）、泄密（`format_display_secrets_in_show_and_select` / `query_cache_share_between_users`）、换解析语义（`dialect` / `compatibility`）、以及纯 SELECT 也会落盘的 `compile_*` 一族
     - 按前缀的：`allow_*`（`allow_ddl` / `allow_experimental_*` / `allow_introspection_functions` / `ai_*` …）、`max_*`、`send_logs_*`、`dynamic_disk_allow_*`、`format_*`、`compile_*`
     - 也就是说**资源上限由服务端 profile 决定**，查询里写 `SETTINGS max_threads = 8`、`max_memory_usage = 0` 会被拒绝（`max_memory_usage = 0` 是不限内存、`max_execution_time = 0` 是不限时长，几条一起写能把整台 ClickHouse 打挂）
   - 设置名按 ClickHouse 的规则解码后再判，藏起来的写法照样拦：反引号 / 双引号标识符（`` SETTINGS `readonly` = 0 ``）、名字里带转义（`` `read\x6fnly` ``）、`SQL_` 前缀的复合名字（`SQL_a.b`）、名字里带空格或逗号（`` `SQL_my setting` ``、`` `SQL_a,b` ``）——这些在 ClickHouse 里都是合法设置名。名字一个读不断：``SETTINGS SQL_a . ` x y` = 2, max_memory_usage = 0`` 里那个带空格的名字在服务端报的是 `Cannot modify 'SQL_a. x y'`，读断了就会把后面的设置整段漏出判定
   - 只读不等于安全：`file()`、`url()`、`remote()`、`mysql()`、`s3()`、`executable()`、`eval()` 这类表函数在只读模式下照样能读服务器文件、出网、跨实例查库，服务端按函数名拦截。两个字符串参数写 `(库名, 表名)` 的表函数（`merge()` / `buffer()` / `timeSeriesTags('system', 'query_log')`）也一样，`FROM` / `JOIN` 后面的相邻字面量会拼成 `库.表` 再判一次。探内省的一并拦掉：`getSetting('readonly')` 实测**不需要任何 grant** 就返回设置值，`getServerSetting()` / `getMergeTreeSetting()` / `getMacro()` 报的是「grant SELECT ON system.…」——它们内部就是去读 `system` 库，`fullHostName()` / `getOSKernelVersion()` / `currentRequestURL()` 能探出主机名与完整请求串。字符串二次解析入口（`formatQuery()` / `parseQueryToJSON()` / `fuzzQuery()` …）也会拦，它们能把判定过的语句改写成别的形态
   - `system` 库整体不可查（`query_log` 能读到别人的 SQL，`users` / `named_collections` 是凭据面），只放行 `system.one` / `system.numbers` / `system.zeros`。库名与表名之间夹的引号、注释、空白都认（`` `system`.`query_log` ``、`system/**/.query_log`），但标识符大小写敏感——`System.IO.FileNotFoundException`、`kube-system.svc`、`/etc/system.d/nginx.conf` 这类文本不构成库引用
   - 未指定顶层 `LIMIT` 时自动补 `LIMIT 1000` 上限（子查询里的 `LIMIT` 不算）；尾部的 `FORMAT` / `SETTINGS` 子句留在 `LIMIT` 之后（`SELECT 1 FORMAT TSV` → `SELECT 1 LIMIT 1000 FORMAT TSV`），整体包一层时留在括号外面。`UNION` / `INTERSECT` / `EXCEPT` 里的 `LIMIT` 只作用于最后一个分支，限不住总量，所以集合运算一律整体包一层 `SELECT * FROM (…) LIMIT n`（`n` 取你写过的最大 `LIMIT` 与 1000 中的较大者），分支内的 `LIMIT` / `ORDER BY` 原样保留。定不出**全局**行数的写法也走包一层的路子：`LIMIT toUInt64(5)` 这类常量表达式、`LIMIT 1 BY x`（按组限行）、`LIMIT 1 WITH TIES`（并列全收，实测返回不限量）、`LIMIT 5e3` / `LIMIT 1_500` / `LIMIT 0x5DC` 这类字面量按真实数值取上限。整体加括号的查询（`(SELECT …)`）后面不能直接写 `LIMIT`（ClickHouse 判语法错误），一律包一层
   - 结尾的分号摘掉（拷贝 SQL 时很常见），中间有分号（多条语句）直接拒绝；引号或注释未闭合的语句直接拒绝；`#` 后面不是空白也不是 `!` 的写法（`SELECT * FROM t #x`）同样直接拒绝——ClickHouse 判它词法错误，放行的话补上的 `LIMIT` 反而会把 `#` 变成注释、把行数上限吃掉
   - 词法与 ClickHouse 完全对齐：`//` 也是行注释、`/* */` 可以嵌套、引号标识符与字符串里的转义解码后再判定（`` `fil\x65`(`` 就是 `file(`）。ClickHouse 词法认的空白比 JS 的 `\s` 宽——U+200B 零宽空格、U+200C / U+200D、U+2060、U+0085、U+180E、U+00A0 都是分词空白，实测 `file​('/etc/passwd')` 照样解析出 `file()`、`system.​query_log` 照样解析出 `system.query_log`，而 `sys​tem.query_log` 报的是语法错误，所以这些码点统一按空白认。定界字符串 `$tag$…$tag$` 只在 token 起点**且**找得到闭合时才是字符串，否则回退成标识符（实测 `$hello$` 是标识符 `` `$hello$` ``、`x$a$hello$a$` 是**一个**标识符），空 tag 的 `$$…` 未闭合才按未闭合拒绝。这里藏得比 ClickHouse 多一点，后面的判定就会整段失效

3. **结果展示**
   - 查询结果以表格形式动态展示列与数据
   - 显示返回行数与查询耗时，错误时展示具体报错信息

### 使用场景

- 自定义数据分析需求
- 复杂的数据分析场景
- 临时性的数据分析任务

### 使用说明

- 表名、列名带 `$` 前缀时需使用反引号包裹，例如：``SELECT * FROM `$final_event_log` LIMIT 100``
- 列名、别名本身是 `UPDATE` / `DELETE` / `SET` 这类写关键字时**不用**再包反引号（`SELECT insert, update, delete FROM sync_stats`、`SELECT 1 AS set` 都能直接跑）；反引号里的是标识符，同样不参与关键字判定
- 单条查询的执行时间有上限限制，复杂查询请合理添加过滤条件
- `settings` / `limit` 当列名或别名是没问题的（`SELECT user_id, settings FROM users WHERE plan = 'pro'`），只有写成 `SETTINGS 名字 = 值` / `LIMIT n` 这种子句形态才按子句处理
- 字符串字面量里的内容会再扫一遍（防止把表名藏进 `remote()`、`viewExplain()` 的参数里）：`system.xxx` 这类库表引用会被拒绝，报错会指出具体是哪个词。函数名只在**代码**里判，字面量里的 `file(`、`url(` 不拦（日志里的 `'remote()'` 文本不该被误伤）。埋点日志里常见的资源设置文本（`'max_threads = 4'`）也不拦
- 已知取舍：字面量扫描是失效即关的，`WHERE msg = 'a=1, readonly = 0'`、`'%dialect=ansi%'` 这种紧跟逗号 / 分号的设置形状文本会被误伤；`max_*` 按策略整个前缀全拦，`system.settings` 里 1852 个真实设置名有 296 个因此被拒，资源上限请到服务端 profile 里用 `<constraints>` 把这些设置逐个 `<readonly/>` 钉死；逗号连接的 `(库名, 表名)` 写法（`FROM t, merge('system','query_log')`）跨了两条引用、拼不回一个 `库.表`，靠 `merge()` 这个函数名本身拦掉
- 上述限制只约束查询本身；跨租户的行级隔离需要在 ClickHouse 侧用 ROW POLICY 或视图保证

## 系统数据分析

### 页面介绍

系统数据分析页面用于监控和分析数据分析系统本身的使用情况，包括查询统计、任务执行情况等。

### 核心功能

1. **统计指标展示**
   - 查询次数：统计时间段内的数据分析查询总次数
   - 查询人数：统计进行数据分析查询的独立用户数
   - 查询平均耗时：统计查询任务的平均执行时间
   - 查询失败率：统计查询任务失败的比例
   - 任务队列状态：显示正在排队、计算中、已终止的任务数量
   - 数据导出统计：统计数据导出次数和导出人数

2. **24小时趋势分析**
   - 以折线图形式展示最近24小时内的查询次数和查询人数趋势
   - 帮助了解系统使用的高峰时段

3. **历史数据查看**
   - 支持自定义日期范围查看历史数据
   - 以柱状图形式展示每日的查询次数和查询人数
   - 默认显示最近30天的数据

4. **任务列表**
   - 展示数据分析任务的详细信息
   - 包括任务名、发起人、任务状态、发起时间、结束时间、耗时等
   - 支持分页查看

5. **数据刷新**
   - 支持手动刷新统计数据
   - 实时更新系统使用情况

### 使用场景

- **系统监控**：监控数据分析系统的使用情况和健康状态
- **性能优化**：通过查询耗时和失败率数据，识别性能瓶颈
- **资源规划**：通过查询趋势数据，规划系统资源分配
- **问题排查**：通过任务列表，排查失败或异常的分析任务
- **使用统计**：统计团队对数据分析功能的使用情况

### 典型应用示例

- 监控系统在业务高峰期的查询压力
- 分析查询失败的原因，优化系统稳定性
- 根据查询趋势，调整系统资源配置
- 查看特定时间段内的任务执行情况，排查问题

## 使用建议

### 选择合适的分析页面

- **转化分析**：使用漏斗分析
- **事件监控**：使用事件分析
- **用户行为**：使用用户路径分析
- **营销效果**：使用归因分析
- **系统监控**：使用系统数据分析或系统数据总览

### 分析流程建议

1. **明确分析目标**：确定要解决什么问题
2. **选择分析页面**：根据目标选择合适的分析页面
3. **配置查询条件**：设置时间范围、筛选条件等
4. **执行查询**：提交查询任务，等待结果
5. **分析结果**：查看图表和数据，进行深入分析
6. **导出数据**：如需进一步分析，可导出数据
7. **制定行动**：根据分析结果，制定优化方案

### 最佳实践

- **定期分析**：建议定期（如每周、每月）进行数据分析
- **对比分析**：通过时间对比、维度对比等方式，发现趋势和差异
- **多维度分析**：从不同维度（时间、用户、渠道等）进行分析，获得全面洞察
- **数据导出**：对于重要分析结果，建议导出保存
- **系统监控**：定期查看系统数据分析，确保系统健康运行

## 常见问题

### Q: 如何选择合适的归因模型？

A: 根据分析目标选择：
- **首次触达归因**：适合分析用户获取渠道
- **末次触达归因**：适合分析最终转化渠道
- **线性归因**：适合分析多触点贡献
- **时间衰减归因**：适合分析时间敏感的场景
- **位置归因**：适合平衡首次和末次接触的贡献

### Q: 漏斗分析的窗口期如何设置？

A: 窗口期应根据业务特点设置：
- **电商购买**：通常设置为7-30天
- **注册流程**：通常设置为1-7天
- **内容消费**：通常设置为1-3天
- 建议根据实际业务数据调整窗口期

### Q: 如何提高查询性能？

A: 
- 缩小时间范围
- 减少筛选条件
- 选择合适的数据维度
- 避免查询过大的数据集

### Q: 数据导出失败怎么办？

A: 
- 检查查询条件是否合理
- 尝试缩小数据范围
- 查看系统数据分析页面的任务状态
- 联系系统管理员
