## 📌 TL;DR（执行摘要）

- **核心目标**：在6个月内将 Probe-X 从 MVP 早期阶段（功能完成度37%）发展为具有市场竞争力的开源 Web 数据分析平台
- **关键决策**：
  1. 作为 MIT 开源项目，聚焦中型互联网/电商/SaaS公司（100-1000人）作为核心目标市场
  2. 差异化定位：微服务架构 + 深度归因分析 + 私有化部署
  3. 优先级：P0（数据准确性、留存分析、用户分群）→ P1（A/B测试、实时监控）→ P2（可视化埋点、移动端SDK）
  4. 不做 SaaS 商业化，专注开源社区运营和技术生态建设
- **下一步**：
  1. 补齐留存分析和用户分群功能（竞品标配）
  2. 提供 Docker Compose 一键部署，降低试用门槛
  3. 强化归因分析差异化（基于阿里 SCM/SPM 模型）
  4. SDK 发布到 NPM，建立社区运营

## 1. 用户研究洞察（来自瑞思）

### 1.1 目标用户群体
- **企业类型**：互联网/科技公司（35%）、电商/零售（25%）、SaaS服务商（20%）
- **企业规模**：100-1000人的中型企业为核心目标
- **核心用户角色**：产品经理、数据分析师、市场营销经理、运营人员、技术负责人

### 1.2 四大核心痛点

| 痛点 | 严重度 | 表现 | 影响 |
|------|--------|------|------|
| 数据准确性与一致性 | 高 | 埋点数据丢失、口径不一致 | 决策依据不可靠，团队信任度下降 |
| 分析灵活性不足 | 中高 | 预设模型无法满足复杂分析需求 | 深度分析需求无法满足，需要额外开发成本 |
| 实时性要求与系统性能 | 中 | 数据延迟影响实时决策 | 错过最佳干预时机，业务损失 |
| 技术集成复杂度 | 中 | SDK接入文档不完善，配置复杂 | 上线周期延长，技术成本增加 |

### 1.3 关键使用场景
1. **电商转化漏斗优化**（产品+数据团队）
2. **营销渠道归因分析**（营销团队）
3. **用户留存分析与干预**（运营团队）
4. **功能使用分析与产品迭代**（产品团队）

## 4. 功能规格书摘要（来自析客）

### 4.1 产品目标
1. **数据准确性**：确保埋点数据采集准确率 > 99.5%
2. **分析灵活性**：支持自定义漏斗、留存、分群等分析
3. **实时性**：数据延迟 < 5分钟，查询响应 < 3秒

### 4.2 核心功能模块（按优先级）

| 优先级 | 功能模块 | 描述 |
|--------|----------|------|
| **P0** | 数据采集与处理 | Web SDK、数据接收服务、数据处理管道、数据质量监控 |
| **P0** | 核心分析模型 | 事件分析、漏斗分析、路径分析、归因分析 |
| **P1** | 用户分群与标签 | 动态分群、静态分群、用户标签、分群洞察 |
| **P1** | A/B测试与实验 | 实验配置、流量分配、效果评估、实验报告 |
| **P1** | 实时数据监控 | 实时仪表板、异常检测、实时告警、实时数据导出 |
| **P2** | 可视化埋点 | 可视化埋点配置、埋点预览、埋点管理、埋点验证 |
| **P2** | 移动端SDK | iOS SDK、Android SDK、React Native SDK、Flutter SDK |
| **P2** | 私有化部署 | Docker容器化部署、Kubernetes编排、数据安全、运维监控 |

### 4.3 Non-goals（明确不做什么）
1. **不支持的功能**：非Web平台原生支持、非标准数据源、高级机器学习、实时流媒体分析
2. **不追求的目标**：大规模企业市场（初期）、全行业覆盖（初期）、全球市场（初期）、替代所有竞品
3. **不采用的策略**：价格战、功能堆砌、过度定制化、激进扩张

### 4.4 技术考量
- **技术栈**：TypeScript + React（前端）、微服务架构（后端）、PostgreSQL + ClickHouse + Redis（数据库）
- **性能要求**：数据接收 10万+事件/秒、查询响应 < 500ms、数据延迟 < 5秒
- **安全要求**：TLS 1.3 加密、AES-256 存储加密、RBAC 访问控制、GDPR/CCPA 合规
